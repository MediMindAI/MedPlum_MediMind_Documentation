Архитектура данных

Модуль склада хранит все складские данные с использованием стандарта FHIR R4 (Fast Healthcare Interoperability Resources). FHIR -- это универсальный язык для медицинских данных: вместо создания собственных таблиц базы данных система отображает каждое складское понятие (поступления, перемещения, остатки) на стандартизированные ресурсы FHIR. Это делает данные переносимыми, проверяемыми и совместимыми с другими медицинскими системами.

Этот раздел охватывает три уровня архитектуры данных:

  • Сопоставление ресурсов FHIR -- какие ресурсы FHIR хранят какие складские данные
  • Модель количества запасов (StockQuant) -- система материализованных складских остатков, обеспечивающая мгновенный поиск запасов
  • Рабочие процессы и бизнес-правила -- состояния перемещений, комплектация FEFO, оповещения и расчет себестоимости

Модель количества запасов

StockQuant -- это ответ системы на простой вопрос: "Сколько товара X находится на складе Y прямо сейчас?" Вместо суммирования всех поступлений и вычитания всех перемещений при каждой проверке запасов (что замедляется по мере роста истории), система поддерживает материализованную запись баланса -- предварительно вычисленный ответ, который автоматически обновляется.

O(1) Время поиска баланса
4-частный Составной ключ
5 Макс. попыток
3 Статуса качества

Составной ключ

Каждая запись StockQuant уникально идентифицируется четырехчастным составным ключом. Представьте это как систему картотеки: комбинация товара, местоположения, партии и статуса качества указывает на ровно одну запись баланса.

Формат ключа: {itemCode}|{locationId}|{lotNumber}|{qualityStatus}

Примеры:
  MED-001|pharmacy-01|LOT-2026A|accepted     -- Амоксициллин, Аптека, Партия A, принято
  MED-001|pharmacy-01|LOT-2026B|quarantine   -- Тот же товар, то же место, другая партия на карантине
  MED-001|lab-02|NONE|accepted               -- Тот же товар, Лаборатория, без отслеживания партий

Без отслеживания партий часть партии хранится как NONE. Статус качества по умолчанию -- accepted.

Поля StockQuant

Поле Расширение FHIR Тип Описание
itemCode sq-item-code string Код продукта (FK на DeviceDefinition)
itemName sq-item-name string Отображаемое имя (денормализовано для производительности)
locationId sq-location-id string ID местоположения отделения/склада
lotNumber sq-lot-number string Идентификатор партии/серии (пусто = без отслеживания)
expiryDate sq-expiry-date date Дата истечения срока годности партии (формат ISO)
qualityStatus sq-quality-status code accepted, quarantine или rejected
quantity sq-quantity decimal Текущее общее количество в наличии
reservedQuantity sq-reserved-qty decimal Количество, зарезервированное для ожидающих перемещений
unitCost sq-unit-cost decimal Средневзвешенная стоимость за единицу (GEL)
unit sq-unit string Единица измерения (таблетка, мл, коробка и т.д.)
lastMovementDate sq-last-movement dateTime Временная метка последнего изменения баланса

Доступное количество: Количество, которое пользователь может фактически использовать или переместить, равно quantity - reservedQuantity. Зарезервированное количество представляет запас, выделенный для утвержденных, но еще не отправленных перемещений.

Оптимистическая блокировка

Когда два человека пытаются одновременно обновить один и тот же складской остаток (например, два поступления на один склад одновременно), система использует оптимистическую блокировку для предотвращения повреждения данных. Как это работает:

  1. Чтение текущей записи StockQuant (включая её meta.versionId)
  2. Расчет нового количества
  3. Отправка обновления с заголовком If-Match ETag, содержащим ID версии
  4. Если кто-то другой обновил запись раньше, сервер возвращает 412 Precondition Failed
  5. Система повторяет попытку с экспоненциальной задержкой (до 5 попыток, со случайным разбросом)

Этот подход избегает блокировок базы данных, гарантируя при этом, что ни одно изменение запасов не будет потеряно даже при конкурентном доступе.

Рабочие процессы и бизнес-правила

Модуль склада применяет автоматические бизнес-правила, управляющие движением запасов в системе. Эти правила обеспечивают нормативное соответствие, предотвращают ошибки данных и оптимизируют оборачиваемость запасов.

Жизненный цикл статуса перемещения

Перемещения между отделениями следуют 9-статусному жизненному циклу с жестко определенными переходами. Это похоже на систему отслеживания посылок -- каждое перемещение может двигаться только вперед через допустимые состояния, а некоторые состояния являются терминальными (изменение перемещения после их достижения невозможно).

Заказы (запросы на снабжение от отделений) следуют более простому жизненному циклу:

Алгоритм комплектации FEFO

FEFO (First Expired, First Out -- первый истекающий, первый выдаваемый) -- это нормативное требование для медицинских материалов. При необходимости использования или перемещения запасов система автоматически предлагает, какую партию выбрать на основе сроков годности -- всегда начиная с партии с ближайшим сроком истечения.

Нормативное соответствие: Комплектация FEFO обязательна для фармацевтической продукции для минимизации потерь от просроченных запасов. Отклонение от рекомендаций FEFO требует документально подтвержденной причины (поврежденная упаковка, запрос клиента, отзыв партии, проблема качества или недостаточное количество).

Алгоритм FEFO работает в три шага:

  1. Фильтрация -- Исключаются все партии с истекшим сроком годности (дата истечения до сегодня) или находящиеся в карантине/отклоненные. Также исключаются партии без доступного количества (полностью зарезервированные).
  2. Сортировка -- Оставшиеся партии сортируются по дате истечения по возрастанию (ближайший срок первый). Партии без даты истечения идут в конец.
  3. Комплектация -- Выбирается первая партия с достаточным доступным количеством (quantity - reservedQuantity >= запрошенное количество).
Логика комплектации FEFO (псевдокод):

1. Получить все StockQuant для (itemCode, locationId, qualityStatus='accepted')
2. Фильтр: убрать где expiryDate < сегодня
3. Фильтр: убрать где (quantity - reservedQuantity) <= 0
4. Сортировка: по expiryDate по возрастанию (null в конец)
5. Для каждого кандидата:
     если availableQty >= requestedAmount:
       вернуть эту партию    -- комплектовать отсюда
6. Если ни одна партия не имеет достаточно: вернуть InsufficientStockError

Порядок комплектации по зонам склада

Когда лист комплектации содержит товары из нескольких складских зон, товары группируются и комплектуются в определенном порядке для безопасности и соответствия нормам:

Приоритет Зона Причина
1 Холодовая цепь Термочувствительные товары должны быть скомплектованы и перемещены первыми для минимизации времени вне холодного хранения
2 Контролируемые Наркотики и контролируемые вещества требуют дополнительной верификации и документации
3 Опасные Опасные материалы требуют специальных мер предосторожности при обращении
4 Общие Стандартные материалы без специальных требований к обращению

Расчет средневзвешенной стоимости

Когда новые запасы поступают по цене, отличной от существующих, система пересчитывает стоимость единицы, используя средневзвешенное. Это гарантирует, что стоимость единицы отражает смешанную стоимость по всем полученным партиям.

Формула средневзвешенной стоимости:

  новаяСтоимость = (существКол x существСтоим + приходКол x приходСтоим)
                   / (существКол + приходКол)

Пример:
  Существующие: 200 таблеток по 0.30 GEL каждая
  Поступившие: 300 таблеток по 0.40 GEL каждая

  новаяСтоимость = (200 x 0.30 + 300 x 0.40) / (200 + 300)
                 = (60 + 120) / 500
                 = 0.36 GEL за таблетку

Особый случай: Бесплатные/пожертвованные товары (стоимость = 0) НЕ снижают существующую стоимость.
  Если существКол > 0 и приходСтоим = 0:
    unitCost остается на существСтоим (без изменений)

Система отслеживает уровни запасов и автоматически генерирует оповещения на основе настраиваемых пороговых значений. Оповещения отображаются на панели управления складом и могут инициировать уведомления.

Тип оповещения Условие срабатывания Серьезность

Истекает (7 дней) expiryDate в пределах ближайших 7 дней Критический (красный)
Истекает (30 дней) expiryDate в пределах ближайших 30 дней Предупреждение (оранжевый)
Истекает (90 дней) expiryDate в пределах ближайших 90 дней Информация (синий)
Просрочено expiryDate в прошлом Критический (красный)

Типы движений запасов

Каждое изменение баланса StockQuant вызвано движением запасов. Система отслеживает семь типов движений, каждое из которых хранится как FHIR SupplyDelivery с определенным кодом типа:

Тип движения Влияние на количество Описание
receipt + Товары, полученные от поставщика
transfer - (источник) / + (назначение) Межотделенческое перемещение запасов
adjustment-plus + Положительная корректировка (при инвентаризации найдено больше ожидаемого)
adjustment-minus - Отрицательная корректировка (повреждение, потеря, сверка)
consumption - Товары, использованные при оказании помощи пациентам
scrap - Утилизированные товары (просроченные, поврежденные безвозвратно)
recall - Отзыв производителя -- товары изъяты из обращения

Холодовая цепь и инспекция качества

Некоторые складские помещения (Лаборатория, Банк крови) требуют дополнительных шагов контроля качества при приемке:

  • Фиксация температуры -- Для товаров холодовой цепи приемный персонал фиксирует температуру в момент получения. Система проверяет, находится ли показание в допустимом диапазоне (например, 2-8 C для лаборатории, 1-6 C для банка крови).
  • Контрольный лист инспекции -- Персонал проверяет целостность упаковки, состояние продукта и полноту маркировки. Товары, не прошедшие инспекцию, помещаются в статус quarantine до рассмотрения.
  • Поток статуса качества -- Товары поступают как quarantine (ожидание инспекции), затем переходят в accepted (допущены к использованию) или rejected (возвращены или утилизированы). Только товары со статусом accepted доступны для перемещений и потребления.

Стратегия расчета баланса

Система использует двойную стратегию для расчета складских остатков:

Метод Производительность Когда используется
Поиск StockQuant O(1) -- мгновенный Основной метод. Читает предварительно вычисленный баланс из ресурса Basic.
Устаревший пересчет O(n) -- медленный Запасной вариант, когда данные StockQuant недоступны. Сканирует до 10 000 записей SupplyDelivery для пересчета из истории.

Кэш балансов использует 30-секундный TTL (время жизни) и поддерживает инвалидацию между вкладками через BroadcastChannel, поэтому когда одна вкладка браузера обновляет запасы, все другие открытые вкладки видят изменение в течение 30 секунд.
