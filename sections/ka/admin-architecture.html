14 Data Flow & FHIR Architecture

14.1 Overview

The Administration module is built on a 5-layer architecture with a strict principle: no shared global state. There is no Redux, Zustand, or any other global state management library. Each page manages its own state through custom React hooks, and cross-domain communication occurs exclusively through FHIR resources persisted on the Medplum server and cache invalidation signals.

  • No shared state -- each page is fully self-contained with its own hook
  • Unidirectional data flow -- Page Component → Custom Hook → Domain Service → FHIR Service → Medplum Client
  • FHIR as the single source of truth -- all inventory data lives on the Medplum server
  • Client-side filtering -- most extension-based filtering happens after fetching from the server
  • Cache invalidation for cross-domain sync -- operations on one page trigger cache clears on related pages

14.3 Cross-Domain Data Flows

The four business domains (Reception, Transfer, Order, Balances) communicate through FHIR resources stored on the Medplum server. The following sections describe the three primary cross-domain flows.

Reception → Balances

When a receipt is created and confirmed, it directly affects the balance of the destination department:

Step Action FHIR Effect Balance Impact
1 Create receipt on ReceptionPage SupplyDelivery created with status=in-progress None (not counted)
2 Confirm receipt SupplyDelivery.status updated to completed Balance increases for destination dept
3 Cache invalidation None Balance cache cleared for affected department
Important: In-progress receipts do NOT affect balances until confirmed. This is by design -- unconfirmed goods should not appear in inventory counts until the warehouse has verified and accepted them.

Transfer Create → Transfer Confirmation → Balances

Transfers involve a two-step process: creation by the source department and confirmation by the receiving department or supervisor:

Step Action FHIR Effect Balance Impact
1 Create transfer on TransferCreatePage SupplyDelivery (type=transfer) created with status=in-progress None (not counted)
2 Supervisor approves on TransferConfirmationPage SupplyDelivery.status updated to completed Source dept decreases, destination dept increases
3 Direct write-off (alternative) SupplyDelivery created directly with status=completed Immediate effect on both departments

Order Create → Order Confirmation

Department orders follow an approval workflow that can optionally trigger automatic transfer creation:

Step Action FHIR Effect
1 Department creates order on OrderPage SupplyRequest created with status=active
2 Warehouse reviews on OrderConfirmationPage SupplyRequest.status updated (confirmed/cancelled)
3 Auto-create transfer (optional) New SupplyDelivery (type=transfer) created from approved order
4 Transfer confirmation Standard transfer confirmation flow applies

14.6 State Management Patterns

The following patterns are used consistently across all custom hooks in the Administration module:

fetchTrigger Pattern

A simple numeric counter that triggers data refetch when incremented:

const [fetchTrigger, setFetchTrigger] = useState(0);

// In useEffect dependency array:
useEffect(() => {
  fetchData();
}, [fetchTrigger, filters]);

// To trigger refetch:
const handleRefresh = () => setFetchTrigger(prev => prev + 1);
Why fetchTrigger?

This pattern allows manual re-fetching without changing any filter values. It is simpler than maintaining a lastFetched timestamp and avoids the complexity of a full state machine.

Cancelled Fetch Pattern

Prevents state updates after a component has unmounted or a newer fetch has started:

useEffect(() => {
  let cancelled = false;

  const fetchData = async () => {
    setLoading(true);
    const results = await fhirService.search(filters);
    if (!cancelled) {
      setData(results);
      setLoading(false);
    }
  };

  fetchData();
  return () => { cancelled = true; };
}, [fetchTrigger, filters]);

medplumRef Pattern

Provides a stable reference to the Medplum client for use in async callbacks:

const medplum = useMedplum();
const medplumRef = useRef(medplum);
medplumRef.current = medplum;

// In async callbacks:
const handleCreate = async () => {
  await fhirService.create(medplumRef.current, data);
};

Client-Side Pagination

Most Administration pages fetch a large batch of results and paginate locally:

// Fetch up to 500 resources from server
const allResults = await medplum.searchResources('SupplyDelivery', {
  _count: '500',
  _tag: 'administration',
  status: 'completed'
});

// Paginate client-side
const page = allResults.slice(
  (currentPage - 1) * pageSize,
  currentPage * pageSize
);

Partial Filter Update Pattern

Filters are updated partially using a spread-based updater function:

const updateFilters = (partial: Partial<BalanceFilters>) => {
  setFilters(prev => ({ ...prev, ...partial }));
};

// Usage:
updateFilters({ departmentId: 'dept-123' });
updateFilters({ showZeros: true, showNegative: true });

14.7 Caching Architecture

The Administration module uses a minimal caching strategy. Only the Balance service maintains a cache; all other data is fetched fresh on each page load.

Cache TTL Scope Rationale
Balance Cache 30 seconds Per department or __all__ Balance computation is expensive (aggregates hundreds of SupplyDelivery resources)
Reception Data None Fresh fetch on each load Mutable list -- users need to see latest receipts immediately
Transfer Data None Fresh fetch on each load Mutable list -- confirmation status can change at any time
Order Data None Fresh fetch on each load Mutable list -- order status can change at any time
Why Only Balance Cache?

Balance computation requires fetching and aggregating potentially hundreds of SupplyDelivery resources, making it the most expensive operation in the Administration module. A 30-second cache provides a significant performance improvement for users who navigate between balance views or change column filters. Other data (receipts, transfers, orders) is displayed as mutable lists where staleness would be immediately confusing to users.

14.8 FHIR Query Patterns

The Administration module uses several common FHIR search parameters when querying the Medplum server:

Parameter Example Purpose
_count _count=500 Limits the number of returned resources (max batch size)
_sort _sort=-_lastUpdated Sorts results by last update date (descending)
_tag _tag=administration Filters by resource tag (primary server-side filter)
status status=completed Filters by resource status (server-side)
supplier supplier=Organization/123 Filters SupplyDelivery by supplier reference
Server-Side vs Client-Side Filtering:

Extensions cannot be searched server-side in Medplum. All extension-based filtering happens client-side after fetching. This means that filters like department, item type, item code, and item name are applied in JavaScript after the FHIR search returns results. Only _tag, status, and supplier can be used as efficient server-side filters.

Filter Distribution

Filter Type Where Applied Examples Performance
Server-Side Medplum FHIR API _tag, status, supplier, _sort, _count Fast -- reduces data transferred over the network
Client-Side JavaScript (in hook/service) Department, item type, item code, item name, price range, expiration range Slower -- full dataset must be fetched first, then filtered in memory

14.9 Error Handling Patterns

The Administration module uses three distinct error handling strategies depending on the operation type:

Pattern 1: Continue with Partial Data

Used by the balance service when aggregating data from multiple sources:

// If one SupplyDelivery fetch fails, continue with others
try {
  const receipts = await fetchReceipts(departmentId);
} catch (error) {
  console.warn('Failed to fetch receipts, using empty array');
  receipts = [];
}
// Balance computed with available data
Rationale: Balance calculation involves multiple API calls. Failing completely because one call errored would prevent users from seeing any balance data. Partial data with a warning is more useful than no data at all.

Pattern 2: Throw to Hook

Used by create operations (receipts, transfers, orders) where failure must be communicated to the user:

// FHIR service throws on create failure
const createReceipt = async (medplum, data) => {
  const resource = await medplum.createResource('SupplyDelivery', data);
  if (!resource.id) {
    throw new Error('Failed to create receipt');
  }
  return resource;
};

// Hook catches and sets error state
try {
  await fhirService.createReceipt(medplumRef.current, receiptData);
  showNotification({ type: 'success', message: 'Receipt created' });
} catch (error) {
  showNotification({ type: 'error', message: error.message });
}

Pattern 3: Return Null

Used by update and delete operations where failure should be handled gracefully:

// FHIR service returns null on update failure
const updateStatus = async (medplum, id, newStatus) => {
  try {
    return await medplum.updateResource({
      resourceType: 'SupplyDelivery',
      id,
      status: newStatus
    });
  } catch (error) {
    console.error('Failed to update status:', error);
    return null;
  }
};

// Hook checks for null
const result = await fhirService.updateStatus(medplumRef.current, id, 'completed');
if (result === null) {
  showNotification({ type: 'error', message: 'Update failed' });
}

Error Handling Summary

Pattern Used By On Failure User Experience
Continue with Partial Data Balance service (read aggregations) Uses empty array, logs warning Shows partial balance data (possibly inaccurate)
Throw to Hook Create operations (receipt, transfer, order) Exception propagates to hook, sets error state Error notification shown, form remains open for retry
Return Null Update/delete operations (status changes) Returns null, logs error Error notification shown, page state unchanged
Network Errors: All three patterns are designed for recoverable FHIR API errors. If the Medplum server is completely unreachable, the Medplum SDK itself will throw a network error that is caught by a top-level error boundary in the React application.
