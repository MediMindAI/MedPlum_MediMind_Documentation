9 Data Model & Architecture

This section documents the FHIR data model, permission system, and business rules that underpin the MediMind Warehouse module. It is primarily intended for developers, system administrators, and integration engineers who need to understand how warehouse data is stored, secured, and processed.

All warehouse resources use the base URL http://medimind.ge/fhir for custom extensions, CodeSystems, and identifier systems. The system currency is GEL (Georgian Lari).

9.1 FHIR Resource Model

The warehouse module uses five core FHIR R4 resources. Each resource type serves a distinct role in the inventory lifecycle: cataloging items, tracking stock movements, managing orders, recording balances, and sending notifications.

Composite Key: {itemCode}|{locationId}|{lotNumber}|{qualityStatus} -- Items without lot tracking use NONE as the lot number placeholder.

Stock Movement Types

Every inventory change creates an immutable StockMove record (modeled as a SupplyDelivery). The system supports seven movement types:

Move Type Direction Description
receipt Inbound (+) Goods received from supplier or another facility
transfer Outbound (-) / Inbound (+) Inter-department transfer (decrements source, increments destination)
adjustment-plus Inbound (+) Positive stock adjustment (physical count correction)
adjustment-minus Outbound (-) Negative stock adjustment (loss, damage, system correction)
consumption Outbound (-) Patient consumption / ward supply dispensing
scrap Outbound (-) Write-off of expired, damaged, or obsolete items
recall Outbound (-) Lot recall removing specific batches from inventory

Adjustment Reason Codes: When creating adjustment-type movements, the system requires a reason code:

  • physical-count -- Correction after physical inventory count
  • damage-spoilage -- Items damaged during storage or handling
  • expired-disposal -- Removal of expired products
  • theft-loss -- Unaccounted inventory loss
  • system-correction -- Technical correction of data entry errors
  • reconciliation -- Periodic balance reconciliation

9.3 Business Rules

The warehouse module enforces several critical business rules to maintain data integrity, security, and regulatory compliance. These rules are implemented at the application layer and cannot be bypassed through the UI.

FEFO (First-Expiry-First-Out)

When picking items for transfer or dispensing, the system automatically suggests the lot with the earliest expiration date. This ensures older stock is used first, minimizing waste from expired products.

Soft Delete

Warehouse items are never physically deleted from the database. Instead, they are marked as inactive using the is-deleted extension on the SupplyDelivery resource. This preserves the full transaction history for auditing and reporting purposes.

  • Deleted items are hidden from search results and dropdowns by default
  • A "Show deleted items" filter allows administrators to view inactive items
  • All historical transactions referencing deleted items remain intact
  • Soft-deleted items can be reactivated if needed

Auto-Generated Codes

The system automatically generates sequential item codes in the format WH-XXXXX (e.g., WH-00001, WH-00002). These codes are assigned at creation time and are immutable. The identifier system used is:

http://medimind.ge/fhir/identifier/warehouse-code

Step-Up Authentication

Certain high-impact warehouse operations require the user to re-enter their password before proceeding. This provides an extra security layer to prevent accidental or unauthorized changes. Operations requiring step-up authentication include:

  • Transfer confirmation -- Approving or rejecting inter-department transfers
  • Write-off confirmation -- Approving the disposal of inventory items
  • Procurement approval -- Approving purchase requests
  • Item editing -- Modifying product catalog attributes in the DeviceDefinition

Dual Department System

MediMind uses two different FHIR resource types to represent departments, depending on the context:

Resource Used For Example
Location Patient assignments (which ward a patient is in) Ward A, ICU Room 3, Emergency Bed 5
Organization Stock tracking and financial charging (which department owns the inventory) Emergency Department, Surgery Department, Pharmacy

The two are mapped by name matching. For example, a patient assigned to Location "Emergency" maps to Organization "Emergency" for stock charging purposes. This dual-ID approach separates physical location management from financial/inventory tracking.

Optimistic UI Updates & Concurrency Control

The warehouse module uses optimistic UI updates for immediate responsiveness. When a user adds an item to a ward's expenditure list, the stock quantity decreases instantly in the UI. If the server operation fails, the change is automatically reverted.

For concurrent access to the same StockQuant record, the system uses optimistic locking with the following strategy:

  • ETag-based locking: Each StockQuant update includes an If-Match header with the resource's meta.versionId
  • Automatic retry: On a version conflict (HTTP 412), the system retries up to 5 times with exponential backoff and random jitter
  • Balance cache: StockQuant balances are cached with a 30-second TTL (time to live)
  • Cross-tab invalidation: Cache invalidation is broadcast across browser tabs using the BroadcastChannel API

Weighted Average Cost

When new stock is received, the unit cost is recalculated using the weighted average formula:

Formula: newCost = (oldQty x oldCost + receivedQty x receivedCost) / (oldQty + receivedQty)
  • Donated items (cost = 0) do not dilute the existing cost -- the previous weighted average is preserved
  • All costs are stored in GEL (Georgian Lari)
  • Cost is tracked at the StockQuant level (per item/location/lot combination)

Warehouse Zones

Items are classified into four warehouse zones for pick list grouping and priority handling. Cold-chain and controlled items are always picked first:

Zone Priority Description
Cold Chain 1 (Highest) Temperature-sensitive items requiring refrigeration
Controlled 2 Narcotics and controlled substances requiring secure handling
Hazardous 3 Hazardous materials requiring special handling procedures
General 4 (Lowest) Standard warehouse items with no special handling requirements
