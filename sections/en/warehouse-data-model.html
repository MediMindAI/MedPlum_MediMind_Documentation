Data Architecture

The warehouse module stores all inventory data using the FHIR R4 standard (Fast Healthcare Interoperability Resources). Think of FHIR as a universal language for health data -- instead of inventing custom database tables, the system maps every warehouse concept (receipts, transfers, stock balances) onto standardized FHIR resources. This makes the data portable, auditable, and interoperable with other healthcare systems.

This section covers three layers of the data architecture:

  • FHIR Resource Mappings -- which FHIR resources store which warehouse data
  • StockQuant Model -- the materialized inventory balance system that enables instant stock lookups
  • Workflows and Business Rules -- transfer state machines, FEFO picking, alerts, and cost calculation

Stock Quantity Model

The StockQuant is the system's answer to a simple question: "How much of item X is in warehouse Y right now?" Instead of adding up every receipt and subtracting every transfer each time someone checks stock (which gets slower as history grows), the system maintains a materialized balance record -- a pre-computed answer that stays up to date automatically.

O(1) Balance Lookup Time
4-Part Composite Key
5 Max Retry Attempts
3 Quality Statuses

Composite Key

Each StockQuant record is uniquely identified by a four-part composite key. Think of it like a filing system: the combination of item, location, lot, and quality status pinpoints exactly one balance record.

Key format: {itemCode}|{locationId}|{lotNumber}|{qualityStatus}

Examples:
  MED-001|pharmacy-01|LOT-2026A|accepted     -- Amoxicillin, Pharmacy, Lot A, accepted
  MED-001|pharmacy-01|LOT-2026B|quarantine   -- Same item, same location, different lot in quarantine
  MED-001|lab-02|NONE|accepted               -- Same item, Lab, no lot tracking

When no lot tracking is used, the lot portion is stored as NONE. The default quality status is accepted.

Available Quantity: The quantity a user can actually consume or transfer is quantity - reservedQuantity. Reserved quantity represents stock that has been earmarked for approved transfers that have not yet shipped.

Optimistic Locking

When two people try to update the same stock balance simultaneously (for example, two receipts arriving at the same warehouse at the same time), the system uses optimistic locking to prevent data corruption. Here is how it works:

  1. Read the current StockQuant record (including its meta.versionId)
  2. Calculate the new quantity
  3. Send an update with an If-Match ETag header containing the version ID
  4. If someone else updated the record first, the server returns 412 Precondition Failed
  5. The system retries with exponential backoff (up to 5 attempts, with random jitter)

This approach avoids database locks while guaranteeing that no stock changes are lost, even under concurrent access.

Workflows & Business Rules

The warehouse module enforces several automated business rules that govern how stock moves through the system. These rules ensure regulatory compliance, prevent data errors, and optimize inventory turnover.

Transfer Status Lifecycle

Transfers between departments follow a 9-state lifecycle with strictly enforced transitions. Think of it like a package tracking system -- each transfer can only move forward through valid states, and some states are terminal (the transfer cannot change after reaching them).

Orders (supply requests from departments) follow a simpler lifecycle:

Current Status Allowed Transitions Description

FEFO Picking Algorithm

FEFO (First Expired, First Out) is a regulatory requirement for medical supplies. When stock needs to be consumed or transferred, the system automatically suggests which lot to pick based on expiration dates -- always using the oldest-expiring lot first.

Regulatory Compliance: FEFO picking is mandated for pharmaceutical products to minimize waste from expired inventory. Overriding FEFO recommendations requires a documented reason (damaged packaging, customer request, lot recall, quality issue, or insufficient quantity).

The FEFO algorithm works in three steps:

  1. Filter -- Exclude all lots that are expired (expiry date before today) or quarantined/rejected. Also exclude lots with no available quantity (fully reserved).
  2. Sort -- Sort remaining lots by expiry date ascending (earliest expiry first). Lots with no expiry date go to the end.
  3. Pick -- Select the first lot with sufficient available quantity (quantity - reservedQuantity >= requested amount).
FEFO Picking Logic (pseudocode):

1. Get all StockQuants for (itemCode, locationId, qualityStatus='accepted')
2. Filter: remove where expiryDate < today
3. Filter: remove where (quantity - reservedQuantity) <= 0
4. Sort: by expiryDate ASC (nulls last)
5. For each candidate:
     if availableQty >= requestedAmount:
       return this lot    -- pick from here
6. If no single lot has enough: raise InsufficientStockError

Warehouse Zone Picking Order

When a pick list contains items from multiple warehouse zones, items are grouped and picked in a specific order for safety and compliance:

Priority Zone Reason
1 Cold Chain Temperature-sensitive items must be picked and moved first to minimize time outside cold storage
2 Controlled Narcotics and controlled substances require additional verification and documentation
3 Hazardous Hazardous materials need special handling precautions
4 General Standard supplies with no special handling requirements

Weighted Average Cost Calculation

When new stock arrives at a price different from existing stock, the system recalculates the unit cost using a weighted average. This ensures that the cost per unit reflects the blended cost across all received batches.

Weighted Average Cost Formula:

  newUnitCost = (existingQty x existingCost + receivedQty x receivedCost)
                / (existingQty + receivedQty)

Example:
  Existing: 200 tablets at 0.30 GEL each
  Received: 300 tablets at 0.40 GEL each

  newCost = (200 x 0.30 + 300 x 0.40) / (200 + 300)
          = (60 + 120) / 500
          = 0.36 GEL per tablet

Special case: Free/donated items (cost = 0) do NOT dilute existing cost.
  If existingQty > 0 and receivedCost = 0:
    unitCost stays at existingCost (unchanged)

Stock Movement Types

Every change to a StockQuant balance is caused by a stock movement. The system tracks seven types of movements, each stored as a FHIR SupplyDelivery with a specific type code:

Movement Type Effect on Quantity Description
receipt + Goods received from a supplier
transfer - (source) / + (destination) Inter-departmental stock movement
adjustment-plus + Positive adjustment (physical count found more than expected)
adjustment-minus - Negative adjustment (damage, loss, reconciliation)
consumption - Items consumed in patient care
scrap - Items disposed of (expired, damaged beyond use)
recall - Manufacturer recall -- items removed from circulation

Cold Chain and Quality Inspection

Certain warehouse locations (Laboratory, Blood Bank) require additional quality control steps during receiving:

  • Temperature Capture -- For cold-chain items, the receiving staff records the temperature at the time of receipt. The system validates whether the reading is within the acceptable range (e.g., 2-8 C for laboratory, 1-6 C for blood bank).
  • Inspection Checklist -- Staff verify packaging integrity, product condition, and labeling completeness. Items that fail inspection are placed in quarantine status until reviewed.
  • Quality Status Flow -- Items enter as quarantine (pending inspection), then move to accepted (cleared for use) or rejected (returned or disposed). Only accepted items are available for transfers and consumption.

Balance Calculation Strategy

The system uses a dual strategy for calculating inventory balances:

Method Performance When Used
StockQuant Lookup O(1) -- instant Primary method. Reads the pre-computed balance from the Basic resource.
Legacy Recomputation O(n) -- slow Fallback when StockQuant data is not available. Scans up to 10,000 SupplyDelivery records to recompute from history.

The balance cache uses a 30-second TTL (time-to-live) and supports cross-tab invalidation via BroadcastChannel, so when one browser tab updates stock, all other open tabs see the change within 30 seconds.
