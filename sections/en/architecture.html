3 Architecture

The MediMind Patient Registration module is built with a component-based architecture using React, TypeScript, and the Medplum FHIR platform. This section provides a technical overview of the system's structure, data flow, and FHIR resource integration.

FHIR Workflow

The patient registration process follows a multi-step FHIR resource creation workflow that integrates search, form submission, and encounter creation.

sequenceDiagram participant User participant SearchHero participant Form participant Hook as useRegistrationForm participant Service as patientDataBindingService participant API as Medplum FHIR API participant Storage as localStorage User->>SearchHero: Enter Personal ID or Name SearchHero->>API: GET /Patient?identifier=01011055555 API-->>SearchHero: Patient[] (existing patients) alt Patient Found SearchHero->>Form: Autofill Patient Data Form->>User: Show "Active Visit Warning" if Encounter.status=in-progress else Patient Not Found SearchHero->>Form: Expand All Sections (New Registration) end User->>Form: Fill Registration Fields Form->>Storage: Auto-save Draft (every 1s debounce) User->>Form: Click Submit Form->>Hook: Validate & Process Form Data Hook->>Service: Bind 101+ GoodKey Codes Service->>API: POST /Patient (create/update) API-->>Service: Patient Resource opt Create Visit = true Service->>API: POST /Encounter API-->>Service: Encounter Resource opt Has Insurance Service->>API: POST /Coverage (for each insurer) API-->>Service: Coverage[] end opt Has Guardian Service->>API: POST /RelatedPerson API-->>Service: RelatedPerson Resource end end Service->>Storage: Clear Draft Service-->>User: Success Message + Navigate to Patient History

Workflow Steps

  1. Search Phase: User enters Personal ID or name → System queries FHIR server for existing patients
  2. Patient Lookup: If found, autofill patient data and check for active visits; if not found, expand all form sections for new registration
  3. Form Filling: User fills 9 accordion sections with auto-save to localStorage (1-second debounce)
  4. Validation: System validates Personal ID (11-digit Luhn checksum), required fields, and business rules
  5. FHIR Resource Creation: On submit, creates Patient resource with 101+ GoodKey data binding codes
  6. Encounter Creation (Optional): If "Create Visit" toggle is ON, creates Encounter, Coverage (if insured), and RelatedPerson (if guardian present)
  7. Draft Cleanup: Clears localStorage draft and navigates to Patient History view
Active Visit Warning: If a patient already has an Encounter.status='in-progress', the system displays a warning modal to prevent duplicate active visits.

FHIR Resources

The registration module creates and manages the following FHIR R4 resources with Georgian-specific extensions.

Resource Purpose Key Fields
Patient Core patient demographic data identifier (Personal ID), name (HumanName with patronymic extension), gender, birthDate, telecom (phone, email), address, extension:citizenship, extension:unknown-patient
Encounter Patient visit/appointment record status (planned, in-progress, finished), class (outpatient, inpatient, emergency), type (visit type), subject (reference to Patient), participant (practitioners), period (visit date/time)
Coverage Insurance policy information payor (insurance company reference), beneficiary (reference to Patient), relationship (self, family), period (policy validity), identifier (policy number)
RelatedPerson Guardian/representative for minors or incapacitated patients patient (reference to Patient), relationship (parent, guardian, spouse), name (HumanName), telecom (contact info), address
Organization Hospital departments, insurance companies identifier, name, type (dept, prov, ins), telecom, address

MediMind extends FHIR R4 to support Georgian healthcare requirements:

Auto-Save and Draft Recovery

The registration form includes intelligent auto-save to prevent data loss:

  • Trigger: Auto-save activates 1 second after the user stops typing (debounced)
  • Storage: Draft data stored in localStorage keyed by patient Personal ID
  • Draft Badge: A visual indicator appears in the progress tracker when a draft is saved
  • Recovery: On page reload, the system detects drafts and prompts the user to restore or discard
  • Cleanup: Drafts are automatically deleted after successful form submission
Business Rule: Minor patients (<18 years old) automatically trigger the Guardian section to become required. The system detects age based on the entered birth date.
