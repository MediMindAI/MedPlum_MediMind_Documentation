Selling

The Selling module manages the sale of inventory items to external buyer companies. When goods are sold, they are removed from a department's stock and a selling waybill document is generated. Each selling transaction flows through a two-step approval process -- the operator creates the waybill, and an authorized user confirms or rejects it.

FHIR Resource: Each selling line item is stored as a SupplyDelivery resource with type code selling. Status lifecycle: in-progress (pending) → completed (confirmed) or abandoned (rejected).

Filters

The filter panel supports 7 search criteria with a collapsible layout:

  • Date From / Date To -- filter by date range
  • Department -- dropdown of inventory departments
  • Warehouse Group -- filter by product category
  • Buyer -- dropdown of all buyer companies
  • Item Search -- text search by product name
  • Document Number -- search by document number

A summary footer at the bottom displays the total record count and the sum of all filtered selling values in GEL.

Correction Action

For completed selling records, a Correction button appears in the actions column. This opens the Warehouse Correction Modal, allowing authorized users to adjust quantities or reverse transactions after the fact.

1.4 Creating a Selling Waybill

Click the "Create Waybill" button in the page header to open the dual-panel creation modal. The modal uses the shared BookModal layout (the same dual-panel interface used for transfers and orders).

Modal Header Fields

Field Required Description
Date Yes Transaction date (defaults to today)
Document Number Auto Auto-generated in format SELL-{timestamp}; field is read-only
Department Yes Searchable dropdown of inventory departments; changing this reloads the available stock in the left panel
Buyer Yes Searchable dropdown of buyer companies loaded from the suppliers-clients data file; deduplicated by company code

Dual-Panel Item Selection

The modal body contains two panels:

  • Left Panel (Available Stock) -- shows all items currently in stock at the selected department. Click an item to move it to the right panel. A filter bar narrows results by name or code.
  • Right Panel (Selected Items) -- items chosen for this waybill. Each item displays editable quantity and selling price fields. The selling price defaults to the cost price but can be adjusted. Items exceeding available stock show an error indicator.

A totals bar at the bottom summarizes the total number of items and the total selling value.

Step-Up Authentication: Before submitting the waybill, the system prompts for password re-entry (step-up authentication). This prevents unauthorized selling transactions even if a session is left open.

Unsaved Changes Warning

If you close the modal while items are still in the right panel, a browser confirmation dialog appears asking whether you want to discard your unsaved changes.

1.5 Pending Confirmation

Newly created selling waybills start with in-progress status and appear in the Pending Confirmation tab. Authorized users can review each document group and either confirm or reject it.

Action Button Effect
Confirm Green button Sets all items in the group to completed status. Inventory is deducted from the department's stock.
Reject Red button Opens a rejection reason modal. Sets all items to abandoned status. Items remain in stock.

Both actions require step-up authentication (password re-entry) and the confirm-selling permission. Administrator users bypass the permission check.

The confirmation table groups items by document number, showing an expandable/collapsible detail view with all line items, their quantities, prices, and totals.

Returns to Supplier

The Returns module handles sending items back to their original supplier. This is typically used for defective goods, expired products, or items received in error. Returns follow the same three-tab layout and dual-step approval process as Selling, but with a key difference: Returns link back to the original receiving waybill so the supplier knows which shipment the items came from.

FHIR Resource: Each return line item is stored as a SupplyDelivery resource with type code return. Status lifecycle: in-progress (pending) → completed (confirmed) or abandoned (rejected).

The returns page mirrors the selling layout exactly, with three tabs and a "Create Return" button in the header:

2.4 Creating a Return

Click the "Create Return" button in the page header. The return creation modal uses the same dual-panel layout as selling, but adds two unique fields: Supplier and Receiving Waybill.

Modal Header Fields

Field Required Description
Date Yes Transaction date (defaults to today)
Document Number Auto Auto-generated in format RET-{YYYY}-{NNN}; field is read-only
Department Yes Searchable dropdown of inventory departments
Supplier Yes Searchable dropdown filtered to only show suppliers (type = "supplier"). This is the key difference from selling.
Receiving Waybill No When a supplier is selected, this dropdown auto-populates with waybill numbers from previous receiving shipments from that supplier. Format: WAYBILL_NUMBER (DATE, X items). Disabled until a supplier is chosen.
Receiving Waybill Lookup: When you select a supplier, the system automatically queries for all previously received waybills from that supplier. This lets you link the return to a specific incoming shipment, which is essential for supplier reconciliation and accounting.

Dual-Panel Item Selection

The item selection works identically to the selling modal:

  • Left Panel -- available stock at the selected department, filterable by name/code
  • Right Panel -- selected items with editable quantities. Unlike selling, returns do not have an editable selling price field (items are returned at their original cost price)

Submitting the return requires step-up authentication (password re-entry). Items that exceed available stock are blocked from submission.

2.5 Pending Confirmation

The confirmation workflow for returns is identical to selling:

  • New returns appear with in-progress status
  • Confirm (green) sets items to completed and deducts stock
  • Reject (red) opens a rejection reason modal and sets items to abandoned
  • Both actions require step-up authentication and the confirm-return permission

Selling vs Returns: Side-by-Side Comparison

Both modules share the same underlying architecture and UI patterns. The table below summarizes where they differ:

Aspect Selling Returns
Direction Items leave the hospital to an external buyer Items leave the hospital back to the original supplier
FHIR Type Code selling return
Doc # Format SELL-{timestamp} RET-{YYYY}-{NNN}
Counterparty Field Buyer (all companies) Supplier (filtered to type "supplier" only)
Receiving Waybill Not applicable Optional dropdown linking to a prior receiving shipment
Price Column Editable "Selling Price" (can differ from cost) Read-only "Price" (returns at original cost)

Heatmap Axes Department → Buyer Supplier → Department
Approval Permission confirm-selling confirm-return

3.1 Shared Workflow

Both modules follow the same end-to-end process:

1
Create Waybill / Return

Operator selects department, counterparty, and items using the dual-panel modal. Step-up auth required.

2
Pending Confirmation

Items are created with in-progress status. They appear in the Pending Confirmation tab for review.

3
Confirm or Reject

Authorized user reviews and confirms (deducts stock) or rejects (returns to stock). Step-up auth required.

4
History & Analytics

Completed and rejected items appear in the History tab. Analytics update in real time with KPIs and charts.

3.2 Permission Reference

Permission Module Grants Access To
confirm-selling Selling Confirm or reject pending selling waybills in the Pending Confirmation tab
confirm-return Returns Confirm or reject pending return waybills in the Pending Confirmation tab
Administrator Override: Users with administrator privileges automatically have access to both confirm and reject actions, regardless of individual permission settings.

3.3 Mobile Experience

Both selling and returns tables switch to a mobile card layout on screens narrower than 768px. Each card shows:

  • Product icon and item name at the top
  • Date and status badge
  • Department and counterparty (buyer or supplier) information
  • Quantity, unit price, and total amount

The card layout preserves all essential information while fitting naturally on smaller screens. Columns that are hidden on mobile (such as Unit, Doc #, and counterparty) are incorporated into the card body as secondary text.
